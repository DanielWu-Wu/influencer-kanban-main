# 2.0 项目进度计划书：红人合作自动化工作台

编制日期：2026-09-10。状态：规划稿，待分阶段实施。

本文件只记录计划，不代表已授权改数据库、部署配置、账号权限或执行真实发送、写飞书。现有人工确认规则继续有效，未来自动化必须经过对应范围的明确授权。

## 1. 版本目标与当前基线

建议把本轮升级定位为 2.0.0：从“人工操作、AI 辅助的工具集合”，升级为“系统主动发现变化、执行已授权任务、人工处理异常的工作台”。版本名称不是上线证据；只有下列关键流程完成验收才发布正式版。

本地核对基线为 main / f2dd036，与本地 origin/main 相同；源码界面版本为 1.2.6。Vercel 当前生产指向未在本轮核实。

- 已有：红人录入、资料解析、飞书字段映射与查重、双邮箱、AI 翻译与起草、人工保存草稿、合作项目、每日待办、日历、任务进度。
- 已有但体验不统一：AI 辅助回复具备直接发送，需先修改中文并重新翻译才能解锁；AI 模板回复主要提供保存草稿。
- 已有可复用基础：YouTube resolve 路由通过上传播放列表读取近期视频，并读取播放量、点赞数和评论数。
- 本地未提交：双邮箱收件箱检测新来信后触发红人预翻译；上一轮 292 项逻辑测试、类型与相关 lint 检查通过，但未部署、未做真实邮箱验收。
- 本计划新增功能尚未开发。本轮不修改 README.md、HANDOFF.md 或既有未提交代码。

## 3. 提醒接通主流程：具体体验

当前提醒页仍依赖另一套 influencers 数据，发邮件使用 mailto；主红人列表则主要展示飞书。提醒和业务对象之间的连接较弱。

目标不是再加一个提醒页，而是让同一件事只记录一次：

1. 在合作项目 A 中选择“下周二跟进视频发布时间”。
2. 系统创建一条任务，关联项目、红人、负责账号、邮箱和具体会话。
3. 每日待办与日历展示同一任务，而不是分别复制一份。
4. 点击任务打开对应项目或正确邮件会话，不跳到外部默认邮件软件。
5. 完成任务同步更新这条任务的状态；“回复已发送”不自动等于“视频已确认上线”。

任务建议状态：待处理、等待对方、稍后提醒、已完成、已取消。未完成事项不能因发现窗口超过 72 小时而消失。

视频发布异常、邮件回复、Follow Up 停止原因都可生成相同类型的任务。使用“业务对象 + 触发事件”防止重复提醒。暂停、完成、恢复均留下记录。

旧提醒先建立映射预览；无唯一对应的旧红人保留原内容并标记待关联，不能猜测归属。日期统一使用明确时区，避免 UTC 文本被当作本地时间。

验收：一个项目提醒同时出现在待办与日历；从任一入口完成后另一入口同步；切账号无法打开别人的会话；八天前未完成任务仍在。

## 4. 统一邮件读取：分两步建设

### 4.1 含义

不是关闭所有刷新，也不是把所有请求塞进一个巨大接口。是让收件箱、每日待办、预翻译和 Follow Up 共用“邮箱同步层”，各功能读取它的结果，不各自重复扫描整箱。

例如同一轮发现三封来信：同步层读取变化并发布消息；列表更新显示；待办匹配红人；翻译读取已有正文；Follow Up 对相关会话暂停。后三个功能不再各自重新获取同一批正文。

### 4.2 第一步：浏览器内统一协调

- 建立公共邮件读取入口，替换当前分散调用；缓存键包含系统用户、邮箱账号、消息/线程编号、内容版本和读取完整度。
- 同一请求进行中时复用结果；列表摘要不能假装成完整正文；新来信使对应旧会话缓存失效。
- 前台打开正文优先，后台待办与预翻译排后；每个邮箱设并发与请求预算。
- 遇到限流统一等待再试，不让多个模块各自反复重试；失败保留旧结果并注明时间。
- 跨标签页协调可用浏览器消息通知和主标签页机制；它只解决同一浏览器，不解决其他设备。
- 显示本轮完成/部分完成、剩余任务数和最近成功时间；分页分批补齐，不静默丢掉第 51 个会话。

### 4.3 第二步：服务端持久化同步

为了关网页后继续运行，需要把同步进度和任务状态放到服务端。

- Gmail：初次建立有限范围的基线，保存 historyId；之后按 history.list 获取变化，只补读变化邮件。历史游标失效时按受控范围补同步，不能无限重扫。
- 腾讯：独立 IMAP 适配，使用文件夹、UIDVALIDITY、UID 识别变化。UID 重建、移动、已发送目录以及标准关系头单独处理，不套用 Gmail 游标。
- Supabase：保存账号隔离的邮件索引、同步游标、任务、锁、尝试次数及结果；正文按需要最小化存储并设保留规则，不复制整箱附件。
- Vercel：运行接口和短批次任务。Cron 只负责唤醒工作，不代表持久任务队列；每批完成后保存游标，接近时限时可续跑。
- 短批次必须有真实的后续唤醒机制。若一天一次 Cron 无法在时限内消化队列，就需要另行选择和批准更频繁的调度或可靠队列，不能仅在数据库中写“待处理”就声称能持续运行。
- Gmail 与腾讯实现可以不同，对用户显示的状态、失败重试和任务结果应一致。

所有服务端自动化重新检查任务所属用户仍有效、邮箱仍连接、授权仍启用。账号停用或撤销授权后，不允许排队任务继续执行外部操作。

### 4.4 同步频率建议

- 人正在看邮箱：保留合理刷新频率，先减少重复读取，不急着追求秒级。
- 无人值守视频监测/统计：第一版每天一次。
- 自动 Follow Up：每天评估到期任务，但每封真实发送前必须重新核对回复。
- 邮件实时推送作为后续选项：Gmail watch/Pub/Sub 有订阅续期和运维成本；不是第一版必须项。

验收：同一批邮件不会因打开待办/翻译重复读取；跨标签页重复请求被合并或排队；部分失败不冒充全部成功；任务中断后从已保存进度继续；关网页后获准的后台任务仍能执行。

## 5. 合作视频监测

建议界面命名为“合作视频发布监测”，使用“疑似提前发布/已发布未登记”，不要直接标记“偷偷发布”或认定违约。

输入：合作项目编号、频道 ID、产品型号及别名、品牌词、已知专属链接/折扣码、约定发布日期或时间、监测起止范围。

流程：

1. 读取该频道上传播放列表，检查上次检查之后的新公开视频，必要时补分页。
2. 用频道归属、发布时间、标题、简介中的产品/品牌/专属链接筛选候选。
3. 规则足够明确时显示强匹配；其余可让 AI 辅助说明依据，不只返回一个无解释分数。
4. 产生待确认提醒，列出视频链接、实际公开时间、约定时间、命中依据。
5. 用户确认后绑定合作项目，再根据已授权字段更新飞书；拒绝匹配后同一候选不重复提醒。

第一版发现与认定分离：同品牌旧视频、同型号其他合作、多项目、直播/首映和时区差异都可能误匹配。没有约定时间只能说“已发布未登记”，不能说“提前”。只知道日期时按已确定业务时区按日比较，不编造时分。

边界：普通公开 API 不能保证发现未提供链接的非公开/不公开视频，也不能保证识别只在画面中短暂出现、标题简介没有线索的合作内容。每天一次只能承诺在下一次成功检查时发现，不承诺实时拦截发布。

一个项目允许绑定多个视频；一个视频涉及多个产品/项目时，需要明确关联，统计时按视频 ID 去重，避免重复汇总。

验收：同一视频只产生一次提醒；无关视频不自动推进项目；缺失发布日期不误报提前；视频下架显示不可用而非播放量清零。

## 6. 视频数据与看板分工

### 6.1 第一版建议：项目采集，飞书复盘

项目负责：确认视频身份、定时获取播放/点赞/评论、最近采集时间、异常、更新记录，以及“已监测/待确认/采集失败”轻量概览。

飞书负责：你熟悉的筛选分组、业务复盘、人工维护的订单数与销售额。按实际字段映射写入，不硬编码字段名。

不要双向随意同步同一字段：

| 数据 | 主来源 | 系统可做什么 |
| --- | --- | --- |
| 播放量、点赞、评论 | YouTube API | 写入明确标记为自动采集的字段，带采集时间 |
| 订单数、销售额、业务备注 | 用户/飞书 | 不自动覆盖，不用 AI 猜测 |
| 项目与视频的关联 | 用户确认记录 | 保存绑定证据，处理多对多关系 |
| 任务、同步进度、操作日志 | Supabase | 技术运行状态，不冒充业务事实 |

API 字段缺失、评论关闭、请求失败等状态与真实 0 区分。旧值保留并标注过期；同批失败只补失败项目。已知视频优先批量读取，不逐个搜索频道。

### 6.2 历史趋势的必要限制

最新值只能回答“现在有多少”，不能还原以前每天的数值。历史趋势需要采集时点记录，而且不能对监测开始前的数据倒填猜测。

YouTube 对未获频道所有者授权的数据有存储时限，对衍生指标也有限制。第一版默认最新值与合规短期记录，不承诺永久免费无限历史曲线；超过 30 天的原始历史统计保留、长期趋势和派生指标，实施前必须确认适用授权与平台规则。复制到飞书并不能绕过这些规则。

因此首发不增加自定义播放衍生评分、自动 CPM/ROI 或虚构转化率；用户的订单销售数据标为独立业务数据。未来确需长期频道分析，再评估频道授权接入与合规数据方案。

建议 2.0.1 再根据实际复盘习惯决定是否自建完整数据看板。2.0 不需要为了版本号重复建设飞书已经能完成的报表。

## 7. 放权与直接发送

### 7.1 精简重复预览

对人工发起的一批录入，在一个入口统一展示对象、数量和将写入的字段。完成一次审核后，后续按已确认方案执行，最后给出成功/失败清单；不要同一份数据重复弹窗。

仅异常要求单独确认：匹配冲突、覆盖已有值、字段映射变化、收件人不明确、任务范围超出原授权。新字段、新表、删除、权限和密钥仍不在普通写入授权内。

### 7.2 设置页不是一个“全权 AI”按钮

| 可授权动作 | 默认建议 | 必须限制的范围 |
| --- | --- | --- |
| 自动翻译/生成候选正文 | 可以启用 | 账号、对象、模型预算、并发 |
| 自动创建邮箱草稿 | 单独选择 | 邮箱、收件人、模板、重复检查 |
| 飞书自动写入 | 分字段选择 | 表、映射、允许新增还是覆盖、日志 |
| 人工审核后直接发送 | 明确点击发送 | 最终内容、收件人、发送邮箱、附件 |
| 自动 Follow Up | 单独主动启用 | 名单、模板、三次上限、间隔、时区、发送上限、到期时间 |
| AI 无人审核处理所有回复 | 不属于 2.0 首发 | 报价、承诺、争议等转人工 |

授权保存在服务端并绑定规则版本；执行时复核，而非只靠前端隐藏弹窗。邮箱、模板或范围改变时，旧授权不能自动扩大。

必须有全局暂停、单项目暂停、待执行列表、撤销授权和操作日志。暂停可阻止尚未提交的发送，不能承诺撤回已经被邮件服务器接收的邮件。

### 7.3 两种回复入口统一

AI 辅助回复与 AI 模板回复都提供“保存草稿”和“审核并发送”。用户可以读完并确认，不必故意改几个字再翻译才能解锁。

最终审核绑定内容版本：正文、收件人、语言、附件改变后原确认失效；修改中文后仍需要同步外文。只展示一次清楚的最终审核区，不把确认拆成多次无意义弹窗。

## 8. 自动 Follow Up

触发：已核对首封邮件真实发送，当前邮箱、红人、具体会话和计划绑定正确，用户已启用该计划。

状态：未启用、等待到期、检查回复中、待发送、已发送、因回复停止、人工暂停、检查失败、发送结果待核实、已完成三次。

每次到期执行：

1. 核对授权有效、计划未暂停、未达到三次上限。
2. 同步最新会话，检查人工发送、已有跟进、来信、退信和退订。
3. 有回复则暂停开发信序列并生成待办；自动回复也先暂停/转异常，不当作“没有回复”继续催。
4. 检查失败时不发送；错过日期不在一天内补发多封。
5. 在已批准模板和事实范围内生成正文；缺价格、期限等信息时不自行补造。
6. 发送前再次核对回复、授权和任务状态，获取同计划执行锁。
7. 保存发送尝试标识后发送，成功记录真实消息编号和时间，再更新业务展示。
8. 超时但不知道是否已发出时进入“待核实”，先查已发送记录，不能盲目重发。

间隔按上一次实际发送时间计算，而非草稿时间；人工另行发出同类跟进时重新核对计划。默认建议可用 5/7/10 天作为讨论起点，正式启用前由用户确认，不是本计划直接生效的规则。

边界：外部邮箱的“检查回复”和“发送”无法组成同一个原子操作。最后一刻到达的回信仍可能与发送竞争，不能保证零时间差；通过临发前复核、锁、较短处理窗口、后续可选推送降低风险并记录异常。

先试运行：系统只列出“准备发给谁、为什么发、为什么停”，不发送。人工核对至少一轮完整三次序列所需的逻辑模拟，并安排真实小名单试点，证明无重复后再扩大。

## 9. 技术资源与上线前提

沿用 Next.js + Vercel + Supabase + Gmail/腾讯 + 飞书 + YouTube API，不建议现在重写技术栈。

- Vercel：页面、接口和短任务；Hobby 定时任务频率及时间精度有限，不适合作为精确时刻发送的承诺。
- Supabase：持久化同步状态、任务、授权策略、运行记录和最小必要缓存；需要后续准备迁移草稿并单独批准应用。
- 邮箱：服务端获得当前用户已经授予的必要能力；新发送 scope 如有需要必须走正式授权，不能绕过授权或把令牌放入任务正文。
- YouTube：复用已有密钥与接口；按实际频道数、视频数、分页、重试估算用量，当前云项目实际限额以控制台为准。
- 飞书：现有映射与账号隔离继续使用；新增表/字段另行确认，失败补偿不重新发送邮件。
- 运维：备份、恢复演练、失败告警、用量记录、人工暂停与回滚方案。

重要：Vercel Hobby 官方限定个人非商业用途。该项目服务商业红人推广，不能仅因技术额度够就默认免费方案适用；正式生产自动化前需要选择符合用途的方案。此计划不自动购买或升级。

只做每日视频检查和每日跟进评估可以降低调度压力，但是否够用仍取决于账号、频道、会话数量和执行时长。更频繁的无人值守邮件检查、长任务续跑可能需要额外调度能力；先测量，再批准资源。

## 10. 建议进度表

估算条件：一名主要开发者在 AI 辅助下持续推进，用户负责业务规则与关键验收；沿用现有服务。以下是工作量规划，不是已排期承诺。缺少真实账号数量与调用量，启动时重新估算；不包含外部平台审批等待。

建议 12 周主计划，另留 2 周缓冲。兼职推进按实际投入延长。

| 阶段 | 建议时间 | 交付物 | 进入下一阶段的验收门槛 | 状态 |
| --- | --- | --- | --- | --- |
| P0 基线与安全修正 | 第 1 周 | 核对线上版本；修复未完成待办过期；区分部分读取失败；定义真实发送状态 | 未完成任务不丢；草稿不作为自动化发送依据；回归通过 | 待开始 |
| P1 统一邮件同步 | 第 2–3 周 | 公共请求入口、缓存/去重、预算、后台游标与补同步设计及实现 | 同一邮件不被各功能反复读取；分页/限流/游标失效/账号隔离通过 | 待开始 |
| P2 任务与授权中心 | 第 4–5 周 | 提醒接通待办日历；分级授权；统一审核发送；运行日志和暂停 | 一次审核可完成获准流程；越权/撤权/重复发送模拟被阻止 | 待开始 |
| P3 视频发布监测 | 第 6–7 周 | 频道监测、候选匹配、人工绑定、提前/未登记提醒 | 无关视频不推进项目；同视频不重复提醒；日检查可恢复 | 待开始 |
| P4 视频采集与飞书复盘 | 第 8 周 | 已绑定视频数据更新、字段所有权、缺失值/失败状态、轻量概览 | 不覆盖人工订单销售字段；合规保留策略确认；数据可核对 | 待开始 |
| P5 自动 Follow Up | 第 9–10 周 | 三次序列、只判断试运行、停止条件、临发复核、发送对账 | 回复停发；失败不发；重复运行不重发；超时不盲重试 | 待开始 |
| P6 小范围试点与发布 | 第 11–12 周 | 双邮箱真机验收、小名单试运行、备份/恢复、监控、发布说明 | 用户验收；生产资源合规；严重缺陷关闭；获得发布批准 | 待开始 |
| 缓冲 | 第 13–14 周 | 真实服务差异、异常补偿、平台审批配合 | 不以赶日期代替安全验收 | 预留 |

P1、P2 是自动 Follow Up 的前置条件。视频监测与数据采集共享基础设施，但不依赖自动发信完成。可分小版本交付，不必等全部完成才开始使用安全的改进。

阶段完成必须报告：改了什么、验证证据、未完成项、是否需要新授权；不能用“代码写完”代替“真实业务通过”。

## 11. 2.0 正式发布标准

- 未完成待办不会因时间窗口自动消失；提醒正确定位项目和邮箱。
- Gmail/腾讯共享任务语义，支持各自同步方式和错误恢复。
- 视频监测能发现候选并由用户确认；缺失与失败不会伪装成正常数据。
- 用户只需一次有效审核即可执行已授权动作；授权可撤销、可追踪。
- 两种 AI 回复方式都可审核后直接发送，且内容变化使旧确认失效。
- 自动 Follow Up 最多三次，有回复停发，检查失败不发，发送结果不明先核实。
- 任意任务重复执行、服务重启、账号切换、邮箱断开均不造成越权或重复外部写入。
- 必要迁移、服务权限与正式部署经过单独确认；完成备份与恢复检查。

观察指标：漏掉的待办数量、每封邮件重复读取次数、发现到可阅读中文的时间、人工审核次数、误匹配视频比例、自动任务失败率、重复发送次数。先建立基线，再确定目标，不编造现有数据。

## 12. 后续需要用户决定的业务事项

当前可先按本计划准备，不需用户选择技术实现。到相关阶段再集中确认：

1. 实际使用的邮箱数、合作频道数、需监测的视频数，以及每日大致来信量。
2. 视频每日检查是否够用；提前发布以哪个时区、日期/时刻为准。
3. 飞书哪些表和字段允许自动新增/覆盖；订单、销售额保留人工所有权。
4. 自动 Follow Up 的间隔、发送时段、每日上限、白名单与授权期限。
5. 生产服务预算，以及是否需要频道所有者授权以支持长期视频数据分析。

首封开发信完全无人审核自动发送、自动谈价、自动承诺条件、复杂自建 BI、跨平台视频识别暂不放入首发范围；以后可分别提出并授权。
